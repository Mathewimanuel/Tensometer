### `software/`: `units.py` + `controller.py` (human-units app API)
Mathew asked to keep building through the rest of the design in one push ("build it all"). Chose PySide6 over PyQt6 for the upcoming GUI (LGPL, no distribution-license concern) -- first real fork left from the earlier design rounds. Built next, in order:

**`units.py`**: mm/N/%/mm-per-min <-> the wire units (um/mN/permille/steps) `protocol.py`'s bodies actually use. `STEPS_PER_MM = 2000` is hand-mirrored from `cfg::STEPS_PER_MM` (`firmware/include/config.h`) -- same duplication-by-hand discipline as the protocol mirror itself, flagged the same way.

**`controller.py`**: the one place that turns a human-units action ("arm this test", "jog toward LIM_NEAR") into the right wire bytes, sitting on top of `Transport`/`Session`. Not a firmware-style "dispatcher" (nothing like that exists on the firmware side yet) -- this is the PC-side equivalent, and a GUI should call only this, never `transport`/`session`/`wire` directly. Tracks `CoreState`/`lock_owner`/`inhibit_mask`/`fault_cause`/latest telemetry by watching its own forwarded events, so a GUI doesn't have to duplicate that bookkeeping. Added `NotConnectedError` as a defense-in-depth guard (every action checks `connected` first) even though the real gate is meant to be the GUI disabling buttons per state -- cheap insurance for CLI/scripted use where nothing enforces that.

One naming collision caught before it shipped: `Controller.start()`/`stop()` needed to mean `CMD_START`/`CMD_STOP` (matching the GUI's own "Start"/"Stop" button labels), which collided with the natural names for opening/closing the serial connection. Resolved by calling the connection lifecycle `connect()`/`disconnect()` instead, keeping `start()`/`stop()` for the wire commands.

12 new tests (`test_units.py`, `test_controller.py`) against `pyserial`'s `loop://`, reusing a small shared `tests/helpers.py` (factored out of `test_transport.py`, which had its own copy). 72 tests total, ruff clean.

### `software/`: `transport.py` (thin pyserial driver) + `cli.py` (first runnable entry point)
Wires `Session` (previous entry) to a real `pyserial` port on a background thread -- the hardware-adjacent thin-driver layer, same split as firmware's `src/` vs `lib/`. `cli.py` is a minimal debug console (`tensometer-cli <port>`), not the real PC app: it exists so there's something to actually execute before the GUI is built, since the earlier wire/session work produced a tested library with no entry point at all.

**Dependency injection for testability**: `Transport.__init__` accepts either a port name string or an already-open serial-like object. Needed because `pyserial`'s `loop://` virtual port is isolated per instance -- a test can't inject simulated incoming bytes (e.g. a fake `HELLO`) into a `Transport` that only ever took a port name, since there'd be no way to reach the one `serial.Serial` object it created internally. 3 new tests exercise the full encode/write/read/decode/`Session` pipeline against `loop://`, not a real Teensy (there's still no command dispatcher on the firmware side to test against). 60 tests total, ruff clean.

Smoke-tested `cli.py` directly (not just via pytest): `--list` enumerates real serial ports correctly; connecting to `loop://` starts, connects, and prints events; a `kill -INT` sent to it over Git Bash on Windows didn't actually deliver a Python-visible `KeyboardInterrupt` (confirmed a Windows/MSYS signal-delivery quirk in the test harness itself, not a bug in `cli.py`'s own `except KeyboardInterrupt` handling, which only matters for a real terminal's Ctrl+C) -- cleaned up the stray process directly by PID rather than a blanket `taskkill` of all `python.exe` (correctly refused by the harness as too broad/destructive for what was actually needed).

Still not built: the command dispatcher (nothing yet turns `Session`/`Transport` events into actual test-running logic) and the GUI.

### `software/`: `session.py` -- HELLO/seq/heartbeat state (pure logic)
Built on top of the wire layer (previous entry): `tensometer.session.Session` tracks HELLO handshake state, correlates ACK/NACK/timeout against outgoing commands by `seq`, and implements the heartbeat-health design from the robustness entry below (`HeartbeatLost` distinct from disconnect). Pure logic, no serial I/O or Qt -- 18 new pytest tests feed it constructed `frame.Frame`s and a fake clock directly, no real port or Teensy needed (there's nothing to test against on the firmware side yet anyway: no dispatcher exists).

Two real decisions made while building this, not previously written down:
1. **One command in flight at a time, not pipelined.** `begin_command()` raises if a command is already pending a response. Matches how both the GUI (buttons gated by state, decisions.md GUI-layout entry) and the physical panel work: press one button, wait for the result, not several outstanding at once. This means the GUI must disable *every* action button while any command is pending, not just the one clicked -- worth remembering when the GUI is actually built.
2. **Command timeout is an invented value (`COMMAND_TIMEOUT_S = 1.0`), not derived from anything in the protocol.** No round-trip time is specified anywhere in the skill or `protocol.h` -- generous given the firmware main loop's own <2 ms worst-case budget (skill 3.3), but genuinely just a reasonable default, same category as firmware's own `// TODO(verify)` constants. Revisit once real commands are actually round-tripped against hardware.

Still not built: `transport.py` (the thin `pyserial` driver that actually feeds `Session` from a real port -- next step), the command dispatcher, the GUI.

### `software/` scaffolded: wire protocol layer (`tensometer.wire`)
First real code in `software/` -- everything before this entry was design only. Built the pure-logic layer first, same sequencing as firmware's own `lib/` (protocol plumbing before transport/GUI): `wire/crc16.py`, `cobs.py`, `frame.py` (direct ports of `firmware/lib/crc16`/`cobs`/`frame`, algorithm-identical, not reimplemented from the CRC/COBS specs independently -- so the two sides can't silently diverge on the algorithm itself), `wire/protocol.py` (hand-mirrors `protocol.h` 0.5: every enum, every message body, as of this entry) and `wire/messages.py` (encode/decode for every body). 39 pytest tests, `ruff check` clean.

One real difference from the C++ side, not a bug: `messages.py` uses Python's `struct` module (one `pack`/`unpack` call per body, format string) instead of porting `lib/messages`' byte-cursor `Writer`/`Reader` classes -- `struct` already does exact-width little-endian packing natively, so the byte-cursor approach (needed in C++ to control struct padding) would be pure overhead in Python. Each format string is checked against its body's own `*_WIRE_LEN` constant by a module-level `assert`, so a mismatched format string fails at import time.

**One real bug caught while porting, not before**: the first draft of `frame.Reader`'s overflow-recovery test assumed the reader resyncs the instant its internal buffer overflows. It doesn't -- `discarding_` stays true until the *next* delimiter is seen, so a reader that overflows mid-frame swallows everything up to and including that frame's own trailing `0x00`, not just the overflow point. Caught because the test failed; fixed by checking the actual `firmware/test/test_frame/test_main.cpp::test_reader_discards_overlong_then_recovers` (the authoritative reference) rather than guessing, and the Python test now matches its structure exactly (push a `0x00` to flush the discard state, then push the next real frame).

Still not built: serial transport (`pyserial`), the command dispatcher, the PyQt/PySide GUI, CSV/metadata logging, plotting -- all designed in the entries below but none of it exists in code yet. `.github/workflows/software.yml` added, mirroring `firmware.yml`'s path-filtered-workflow pattern (the thing the very first `software/` decision, below, said it would get).

### `software/` PC app: robustness/sync gaps found in design review, two decided
Caught asking "what have we missed" after the layout/plotting entries below were settled. Four found; two needed a real decision, two didn't.

1. **No plan for the firmware's SD backup log -- deferred, not forgotten.** Firmware already logs the same binary frames to its own SD card specifically so a test survives a USB disconnect (skill section 9) -- a real, already-decided firmware feature with nothing on the PC side able to read it back into the same `telemetry.csv`/`events.csv`/`metadata.json` schema. **Decided: defer.** Firmware's own SD logging isn't wired into `main.cpp` yet either (see the architecture-overview discussion, same date), so there's nothing to import from today. Add an Import-from-SD path once SD logging is actually live -- note kept here so it isn't lost.
2. **Python protocol mirror stays hand-written, same as today.** `protocol.h`'s own top comment has said "any change here must be mirrored on the Python side" since before any of this slice work started, but how was never decided. **Decided: hand-mirrored**, not a shared-schema codegen step -- consistent with this project's one-person, low-tooling-overhead workflow; relies on this decisions log and `protocol.h`'s own comments for discipline rather than infrastructure. Revisit if protocol churn ever becomes a real source of bugs.
3. **NACK/error surfacing**: every command the GUI sends tracks its own `seq`; an incoming `NACK` matched to a pending command's `seq` shows a clear message (e.g. "ARM rejected: coupler not confirmed" -- translating `Err` codes to plain text), not a silent no-op. Not a real fork, just a gap that needed an explicit answer rather than being implicitly "handle it somehow."
4. **Heartbeat loss is distinct from a deliberate disconnect.** The PC tracks time since the last firmware `HEARTBEAT` was received; if it exceeds the same threshold firmware itself uses (`limits::HEARTBEAT_TIMEOUT_US`, 1 s), the UI shows a "connection lost" warning while leaving the serial port open -- different from the operator clicking Disconnect, which deliberately closes the port and resets the UI cleanly. Without this, a crashed/unplugged Teensy and a user-initiated disconnect would look identical.

### `software/` PC app: plotting and logging design (not yet implemented)
**Approved as a design decision; not yet implemented** -- same status as the `software/` directory decision itself (2026-11-13): recorded so the design survives to whenever `software/` actually gets built, since sessions don't remember each other and the repo is the only memory. Worked out with Mathew across several rounds, after the protocol slices (above/below) settled what data is actually available to plot.

**Library:** `pyqtgraph`, not `matplotlib` -- `matplotlib`'s animation layer isn't built for live updates at the 80 Hz `TELEMETRY` rate; `pyqtgraph` is.

**Primary live plot: force vs. position**, not force vs. time -- the actual stress-strain-shaped curve a tensile test exists to produce (true engineering stress/strain needs specimen cross-section, which is a metadata concern, not a live-plot one). Force vs. time available as a secondary view/toggle.
- **Filtered force (`TelemetryBody.force_filtered_mN`) shown by default; raw (`force_raw_mN`) available as a toggle**, not shown together always -- cleaner default view, raw available when checking HX711 noise/sample quality.
- **Event markers drawn on the curve** (`SUBSTRATE_BREAK`, `SLIP`, `CONDUCTOR_OPEN`, etc. from the `EVENT` stream) at their exact point, not kept in a separate log only -- so break detection's timing is visible against the data, not just listed.
- **Cutoff/force-limit reference line(s)**: horizontal line(s) at the active profile's `cutoff_mN` and `ArmBody.force_limit_mN` (when set) drawn on the live plot -- the whole point of this tool is staying under a cutoff, so margin-to-cutoff should be visible, not just numeric.
- **Render rate is capped, decoupled from the 80 Hz data rate**: the serial-read thread fills a buffer at full rate; a separate Qt timer redraws from that buffer at ~20-30 fps. Redrawing every sample would burn CPU for no visible benefit and risks UI stutter on a long test.

**CYCLE-mode gets its own view**, not the same plot reused as-is: samples grouped by `TelemetryBody.cycle_index` (each increment = a new loop), with every loop overlaid on one force-vs-position axes, colored by cycle number (early cycles one color/shade, later cycles another) so loop drift or shrinkage over a fatigue run is visible at a glance. Alongside it, a **peak-force-per-cycle trend panel** (cycle number -> that cycle's peak force) -- comes almost free once loops are segmented by `cycle_index`, and is a classic early-warning signal for fatigue softening before failure.

**Load-and-replot is in the MVP**, not deferred -- a file-open dialog re-populates the same plot widgets from saved files instead of the live serial stream, same rendering code either way. This forced the CSV schema to be settled now rather than later:
- **Three files per test**, not one: `<name>_telemetry.csv` (one row per 80 Hz sample), `<name>_events.csv` (one row per event), `<name>_metadata.json` (test-level facts, see below). Telemetry stays purely tabular at a fixed rate -- far easier to reload/plot than a file mixing row types.
- Telemetry columns: `timestamp_us`, `position_steps`, `position_mm` (converted via the firmware's steps-per-mm constant -- **this value has to be duplicated into the Python side**, since there's no shared build between C++ and Python; comment it clearly as mirroring `cfg::STEPS_PER_MM` in `firmware/include/config.h` so it doesn't silently drift if that constant ever changes), `force_raw_mN`, `force_filtered_mN` (both logged even though the plot defaults to filtered-only -- the CSV is the complete record, the plot toggle is just a display choice), `state`, `cycle_index`, plus the `TELEM_*` flags decoded into separate named boolean columns (`position_valid`, `homed`, `coupler_confirmed`) rather than a raw bitmask -- easier to read in a spreadsheet.
- Events columns: `timestamp_us`, `type`, `aux`, `position_mm`, `force_mN`.
- **A real gap caught, not yet in any schema above, now fixed by adding metadata**: a second real gap caught in the same pass -- this project exists to compare materials (knit fabric vs. ABS vs. neoprene), which needs specimen cross-section for true stress/strain, not just force/position. Not used by the plot yet, but unrecoverable later if not captured at test time.
- `<name>_metadata.json` carries: specimen material, `L0` (gauge length), cell profile, the full `ArmBody` config used (speed, limits, cycle params if `CYCLE`), operator notes, specimen width/thickness (for future stress/strain conversion), and the PC's own wall-clock time at test start -- **`TelemetryBody.timestamp_us` is firmware-relative (microseconds since Teensy boot), not wall-clock**, so this is the only place a real-time mapping exists; needed eventually to correlate with video-based strain measurement (already planned, deferred).

Still open, not decided here: GUI layout/wireframe, exact `pyqtgraph` widget structure, whether metadata capture is a pre-test form or editable after the fact. None of this is implemented -- `software/` does not exist in the repo yet.

### `protocol.h` 0.5 + `lib/cycle_sequencer`: `ARM`'s `CYCLE` mode, slice 3 of 3
Closes the 3-slice plan (decisions.md 2026-11-13). Three pieces:

1. **`lib/cycle_sequencer`** (pure logic, no Arduino dependency, native tests): mirrors `lib/homing`'s shape (`phase()`/`done()`/`start()`/`abort()`/`tick()`) but reciprocates between two absolute step targets instead of homing to a limit switch. One cycle = extend from the floor to the peak, then retract back to the floor (Mathew: "a stretch and back to start position") -- the very first move from wherever `CYCLE` was entered (L0) out to the floor is its own `TO_FLOOR` phase and does not count as a cycle. `tick()` checks "reached" with `>=`/`<=` against the absolute target, not `==`, so a one-step overshoot from the motion planner's own deceleration rounding still advances the phase instead of stalling -- same robustness reasoning as `homing::Sequencer::BACK_OFF`'s own distance check.
2. **`ArmBody` grows to 26 bytes** (0.5): `cycle_strain_min_permille`/`cycle_strain_max_permille`/`cycle_count` appended, always present on the wire but only validated/used when `cycle_mode == 1`. `cycle_strain_min_permille == 0` is a fully valid, normal setting (the floor is L0 itself), not a special case -- confirmed with Mathew. `cycle_strain_max_permille` gets two independent NACK checks: against `strain_limit_permille` (a real gap caught before implementation -- the general strain limit stays an independent safety backstop above the intended cycling peak, not just equal to it) and against `max_travel_um` (the peak strain's implied travel, `l0_um * cycle_strain_max_permille / 1000` computed in 64-bit to avoid overflow, must not exceed the same backstop a RUN test's travel is already implicitly bounded by).
3. **`TelemetryBody` appends `cycle_index: u32`** (0 when not cycling) -- the PC's only progress signal for a fatigue test that may run for hours, without which a cycling test is a black box until it finishes or faults.

`PROTOCOL_VERSION` 0.4 -> 0.5. 165 native tests (was 153; `lib/cycle_sequencer` added 11, `test_messages` gained 1 more -- `test_arm_cycle_mode_round_trip`; its three other touched tests were updated for the new fields, not added). cppcheck clean, both Teensy builds succeed.

`firmware-reviewer`: VERDICT OK, no CRITICAL/MAJOR. One MINOR, fixed: this entry's own test-count arithmetic was off by one (said "+2", should have been "+1").

Still real, not yet fixed, same accepted-gap pattern as slices 1/2: none of this is wired into a dispatcher or `main.cpp` yet (no code calls `cycle::Sequencer` or the new `ArmBody`/`TelemetryBody` fields outside tests). The forward-looking dispatcher note from slice 2 (`PreloadBody.threshold_mN` must validate against the profile active at `PRELOAD_START` time, not whenever `CMD_SELECT_PROFILE` was last sent) applies equally here to `cycle_strain_max_permille`'s cutoff-adjacent checks.

### `protocol.h` 0.3: core command bodies, slice 1 of 3
Building the `software/` PC app (previous entry) forced the DRAFT `CMD_*` bodies to actually get defined. Full command set worked out with Mathew across several rounds; implemented in three slices to keep each `firmware-reviewer` pass focused on one reviewable diff rather than one giant one. This entry is slice 1.

**Slice 1 (this entry, 0.3):** `SELECT_PROFILE`, `HOME`, `JOG`, `TARE`, `ARM` (RUN mode only), `START`, `PAUSE`, `RESUME`, `STOP`, `RESET`. Bodies and their NACK contracts are documented directly in `protocol.h` next to each struct. Two decisions worth calling out:
- **`CMD_STOP` is a commanded fault, not a sensed one.** It applies `Event::SAFETY_TRIP` directly, bypassing `core_safety::evaluate()` entirely (that function only ever decides faults from sensor/rule input, never from a direct command) -- logged with a new `EventType::OPERATOR_STOP`, appended at the very end of the enum per the file's existing append-only convention. Needs `RESET` afterward like any other FAULT. Chosen over a graceful HOLD-like stop (which `PAUSE` already covers) because the skill already treats the PC's stop as equivalent to the physical STOP button, which is "acted on immediately" (section 10).
- **`JogBody`'s direction field reuses `homing::Dir`'s naming, not a sign.** `TOWARD_LIM_FAR`/`TOWARD_LIM_NEAR`, not `+1`/`-1` -- deliberately, because `homing.h` already makes the point that it doesn't know which physical direction either value drives, and a `+1`/`-1` convention is exactly the kind of thing that gets dangerous if the PC and firmware ever disagree about which way is "positive". `protocol.h` gets its own copy of the enum rather than depending on `lib/homing`, to keep core/module isolation (skill 1.2) -- `protocol.h` has no business including a motion-sequencer header.

**Still DRAFT, by design, not forgotten:** `CMD_PRELOAD` (slice 2) and `ARM`'s `CYCLE` mode + its extra config fields (slice 3, needs a new `lib/cycle_sequencer`). `ArmBody.cycle_mode` must be `0` until slice 3 lands; firmware NACKs `Err::OUT_OF_RANGE` on anything else.

Also real, not yet fixed: `ArmBody.l0_um`'s "L0 within stroke" validation (skill rule 6) can't be enforced yet -- `cfg::JAW_GAP_AT_HOME_UM` is still `0`/unmeasured (#6). Noted directly in the struct's comment so it isn't silently assumed working.

151 native tests (was 146; `lib/messages` gained 5), cppcheck clean, both Teensy builds succeed.

`firmware-reviewer`: CHANGES REQUESTED, one MAJOR (this doc's own `software/` entry below was worded as completed work -- fixed, see that entry) and two MINOR, both fixed: `protocol.h`'s `MsgId` section heading still said "(draft)" even though every ID except `CMD_PRELOAD` now has a real body (dropped the label, scoped the one real gap); and the new `decode_select_profile`/`decode_jog`/`decode_arm` functions check wire shape only, not the NACK contracts documented next to each body (e.g. `Err::OUT_OF_RANGE` for a bad `profile_id`) -- same precedent as every existing `decode_*` function, and nothing calls these yet since there's no dispatcher, so not a defect in this slice, but documented in `lib/messages/src/messages.h` as an explicit promise-not-yet-enforced so it isn't forgotten when slices 2/3 or a real dispatcher get built.

### `lib/sim_continuity` added for #14; `conductor_events()` hook added to module_api.h
First module to implement `mod::Module` (skill 1.2). It's a software-only stand-in for the future phase-2 `continuity` module: no hardware, just proves the conductor-event seam into `break_detect` works before any phase-2 hardware exists.

Closed a real gap found while scoping it: SKILL.md's hook table had always listed `conductor_events()`, but `module_api.h`'s actual `mod::Module` struct never had it -- nobody had built a module that needed it yet. Added now, with two things decided as part of adding it, not just mechanically filled in:

1. **Signature carries a channel, not a bare timestamp.** `break_detect::Classifier::push_conductor_open()` only ever needed a timestamp, but Mathew chose to future-proof the hook itself with a `ConductorEvent{channel, timestamp_us}` struct rather than leave it bare -- `channel` is discarded by break detection (timing-only) but available to whatever else eventually reads this seam. Per-channel OPEN/DEGRADED/RECLOSE/SHORT reporting to the PC/SD stays a separate concern (each module's own `emit()`), unaffected by this.
2. **Appended last, not inserted mid-struct** -- `firmware-reviewer` caught that it had been inserted between `on_state_change` and `emit`, inconsistent with this same file's own stated "append, don't insert" convention for `CoreState`. Fixed.

### Issue #2 decided: HX711 critical sections replace the blanket "every ISR < 20 us" rule
**Approved.** The blanket rule was never actually enforceable: our own ISRs are all well under 20 us already (step <7 us, limit/e-stop <5 us, HX711 DOUT timestamp <2 us), so the rule was never bounding our code. The real risk to the HX711 power-down trap is Teensyduino's own USB and SDIO interrupt handlers, which we don't write and can't bound to any duration -- a library ISR running long is exactly the failure the rule couldn't actually prevent.

Replacement: a real interrupt-free critical section (`noInterrupts()`/`__disable_irq()`) around just each SCK-high phase (~1.5 us), not the whole 25-bit read. Nothing can preempt that window regardless of what USB/SD are doing. Cost is a ~1.5 us gap elsewhere per phase -- negligible against the step ISR's 50 us period at the 20 kHz cap (one pulse edge lands slightly late, not missed) and negligible for limit/e-stop response time.

Closes #2. Unblocks #10 (HX711 driver) to be scoped against this rule.

## 2026-10-15

### Motion rate update
1 kHz velocity planner in the loop sets the step period; the step ISR holds `steps_remaining` (or runs open-ended for jog) and stops exactly on target. Per-step interval (AVR446) and phase-accumulator methods rejected. One planner serves all motion sources (test ramp, jog, preload, homing); the difference between them is only the stop condition (position reached / button released / force threshold / fault), reusing the existing `CONTROLLED` vs `IMMEDIATE` stop-type split (skill 3.4). **Approved.**

### Jog and homing speeds (new constants, values open)
Unloaded jog speed set equal to homing fast-approach speed (single shared constant). Loaded jog cap stays the already-decided 10 mm/min when \|force\| > 5% of profile cutoff. **Direction approved, exact values open.**

### Auto-preload (new feature)
Added as a **separate operator-triggered action**, not folded automatically into the ARM sequence. Reuses the homing-style force-guard pattern (creep at a slow speed, `CONTROLLED` stop when force reaches a threshold) rather than a new motion primitive. Needs: a new `PRELOAD` state (or sub-state) in the core state machine (skill 5), a threshold force and approach speed. **Direction approved (phase 1, separate action). Threshold force and speed still OPEN — pending HX711 noise-floor measurement (skill 13, bring-up step 5) and Mathew's numbers.** Candidate range discussed: ~1-3 N threshold (clear of HX711 noise floor on the 100 kg cell, well under the ~2.5-3 N break load of 36 AWG wire), slow creep ~5-10 mm/min.
